# Build, packages and FFI

`build.zen` is a program that builds a graph, as in Zig. Its manifest is a
declarative record of products, targets and versioned dependencies, as in
SwiftPM. A lockfile pins every dependency to a content hash, as in Zig's
`.zon`. FFI is explicit declarations checked against real headers.

Design goals, in order: **small, works, elegant, low attack surface.**

```text
 build.zen ──comptime──► Package (manifest) + Graph (steps)
                              │                  │
 zen.lock ◄── resolve (MVS) ──┘                  │
     │                                           ▼
     └── fetch by sha256 ──► cache ──► compile ──► link ──► install / run / test
                                       (no network after fetch, no code from deps runs)
```

## 1. One file: `build.zen`

```zen
{ Package, Product, Target, Builder, BuildError, from, exact, path } = std.build

// The manifest: data, read without running the graph (SwiftPM's Package.swift)
package* = Package(
    name: "app",
    version: "0.3.0",
    products: [
        Product.exe("app", target: "app"),
        Product.lib("audio_fx", targets: ["fx"]),
    ],
    dependencies: [
        dep("audio", url: "https://github.com/lantos1618/zen-audio.git", version: from("1.2.0")),
        dep("http",  url: "https://github.com/lantos1618/zen-http.git",  version: exact("0.9.1")),
        dep("local_ui", path: "../zen-ui"),                    // local, never fetched
    ],
    targets: [
        Target.exe("app", src: "src/main.zen", deps: ["fx", "audio.player", "http.client"]),
        Target.lib("fx",  src: "src/fx/fx.zen", deps: ["audio.dsp"]),
        Target.test("fx_test", src: "tests/fx.zen", deps: ["fx"]),
        Target.system("sdl", pkg_config: "sdl2", headers: ["SDL.h"], libs: ["SDL2"]),
    ],
)

// The graph: code, for anything the manifest cannot say (Zig's build.zig)
build* = (b :: Builder) Res<BuildError> {
    tracy = b.option(bool, "tracy", false);                  // zen build -Dtracy=true
    app = b.exe(package.target("app"));
    tracy.then({ app.define("TRACY_ENABLE") });
    b.install(app);
    b.step("run", "Run the app").run(app, args: b.args());
    b.step("test", "Run tests").run(b.exe(package.target("fx_test")));
}
```

- **Most packages need only `package`.** `build` is optional. Without it, the runner installs every product and adds `run` and `test` steps.
- **A dependency's `build.zen` contributes only its `package` record.** Its `build` function never runs in a consumer's build (unlike Zig). That removes the biggest supply-chain hole: code from a dependency never executes at build time.

## 2. Products, targets and imports

| Kind | Meaning |
|---|---|
| `Target.exe` / `Target.lib` / `Target.test` | a module root (`src`) and the targets or products it uses |
| `Target.system` | a native library found by pkg-config or explicit paths (SwiftPM's systemLibrary) |
| `Target.c` | C sources compiled into the graph: `sources`, `include`, `defines`. Use sparingly. |
| `Product.exe` / `Product.lib` | what a package offers to the outside; only products are importable by consumers |

```zen
{ play } = deps.audio.player       // <package>.<product module>
dsp = deps.audio.dsp               // a module, bound as a module
```

- **Strict visibility.** A target reaches only the `deps` it lists, and only a dependency's **products**, never its internal targets.
- **No name leaks inside a package.** Bare roots inside a package mean that package's own modules, so it never depends on the name a consumer gives it.

## 3. Versions and resolution

| Requirement | Meaning |
|---|---|
| `from("1.2.0")` | ≥1.2.0, <2.0.0 (SwiftPM's default, up to the next major) |
| `exact("0.9.1")` | that version only |
| `range("1.2.0", "1.5.0")` | ≥ low, < high |
| `rev("<40-hex>")` | a commit, for unreleased work; never a branch |
| `path("../x")` | local source, not locked or fetched |

**Versions are git tags `vX.Y.Z`.** Resolution is **minimal version selection** (Go's MVS): for each package, take the highest of the *minimum* versions anyone requires. It's deterministic, needs no SAT solver, takes about 100 lines, and never moves to a new version unless someone asks. A conflict, such as two incompatible majors, is an error naming both requirers.

## 4. `zen.lock`: the resolved file

```text
# zen.lock — generated by `zen pkg resolve`, committed
audio  https://github.com/lantos1618/zen-audio.git  v1.2.3  3f9c…e1a0  sha256-7b1d…92ce
http   https://github.com/lantos1618/zen-http.git   v0.9.1  a04b…77d2  sha256-c6e0…1f3a
```

- **Each entry records** the package, URL, version, commit and the **SHA-256 of the canonical source tree**: sorted paths, file modes and contents, no `.git`.
- **The cache is content-addressed** under `~/.cache/zen/p/<sha256>/`. Two packages with the same tree share it, and a tampered cache fails its hash.
- **A build never touches the network if `zen.lock` covers the graph.** A missing or mismatched entry is an error: run `zen pkg resolve`. There is no silent update.
- **Line-based text,** so diffs review cleanly.

## 5. Commands

```sh
zen build [step] [-Dname=value] [--target aarch64-linux] [--release]
zen run | zen test                         # the run / test steps
zen pkg add <url> --from 1.2.0             # edits `package.dependencies`, resolves, locks
zen pkg resolve | update [name] | fetch    # lock, bump, populate the cache from the lock
zen pkg why <name>                         # who requires it, and at what version
```

`--offline` is always safe once fetched. Cross-compilation is first class (`--target` uses the `std.build` triples), as in Zig.

## 6. How `build.zen` runs: the low attack surface

```text
build.zen  ──►  comptime evaluator (no Env)  ──►  Package + Graph   (pure data)
graph      ──►  runner executes steps        ──►  compile / cc / link / run
```

- **No `Env` in comptime.** `build.zen` cannot read files, use the network, read the clock, read the environment, or spawn anything. It returns data, it's step-limited, and the same inputs always give the same graph.
- **All effects are graph steps** that the runner performs:
  - compile, cc, link, install, run, and `b.run_tool`;
  - every external tool is called with an **argument array**, never a shell string;
  - every input and output is declared, so caching is exact.
- **Fetching is the package tool's job only:** git or HTTPS archive, then verify sha256, then the cache. There are no install scripts and no post-fetch hooks, and git runs with hooks disabled and no credential prompt.
- **Dependency code never runs at build time.** Only its `package` record is evaluated, also in the no-`Env` evaluator.
- **Native `Target.system` / `Target.c`** are the only way foreign code enters, and they're visible in the manifest.

## 7. FFI

```zen
// Explicit declarations, checked against the real header by the C compiler
Posix* = c.bind("unistd.h", {
    getpid* = () c_int
    close*  = (fd: c_int) c_int
    O_CLOEXEC*: c_int = 0            // macro or enum; fallback only when undefined
})
Timespec* = c.record("time.h", "struct timespec", { tv_sec: c_long, tv_nsec: c_long })
{ callback } = std.native            // callback(f): a named, non-capturing Zen fn as a C fn pointer
```

| Rule | Why |
|---|---|
| Declarations, not header parsing | the binding is reviewable Zen, so there's no hidden import surface |
| The header is included, never a copied prototype | the C compiler checks every signature and ABI |
| Link flags come from the manifest (`Target.system`), never from the binding | one place to audit what gets linked |
| `Ptr<T>` and `c_*` types only cross the boundary | no Zen aggregates or closures leak into C |
| Opt-in `zen pkg bind <header>` generates a `c.bind` file to commit (Zig's translate-c, offline) | convenience without build-time parsing |

## 8. What exists today vs this design

| Today (`~/zen/zen`, `docs/BUILD_PACKAGES.md`) | This design |
|---|---|
| `b.add(name, {url, rev, src, libs, paths})`, commit pins only | `package.dependencies` with versions, `rev` still allowed |
| No lockfile; cache checks git objects | `zen.lock` with sha256 of the source tree, content-addressed cache |
| `build.zen` registration expressions interpreted | `build` runs in the no-`Env` comptime evaluator, effects as graph steps |
| No products; any module of a dep is reachable | `Product` boundary: only exported products import |
| `libs`/`paths` per dep | `Target.system` with pkg-config |
| No `zen pkg` commands | add / resolve / update / fetch / why |

## 9. Size budget (for the hand-written compiler)

| Piece | Budget |
|---|---|
| `std.build` types (Package, Product, Target, Builder, steps) | ≤ 400 lines |
| Graph runner (topological order, caching by input hash) | ≤ 400 |
| Resolver (MVS) + lockfile read/write | ≤ 300 |
| Fetch + tree hash + cache | ≤ 300 |
| `c.bind` / `c.record` / callback lowering | ≤ 400 |
